# macOS Menu Bar App — Project Scaffolding Blueprint

This document describes, use-case-agnostically, how this repository is structured and operated. It is written to be handed to an AI agent (or a human) as the complete blueprint for scaffolding a **new** macOS menu bar app on the same foundation: same layout, same architecture conventions, same build/test/CI/release machinery.

Placeholders used throughout — replace all of them in the new project:

| Placeholder | Meaning | Example |
|---|---|---|
| `<AppName>` | lowercase product name; also the source directory and scheme name | `uptrack` |
| `<bundle-id>` | app bundle identifier | `com.example.app` |
| `<TEAMID>` | Apple Developer Team ID | `ABCDE12345` |
| `<github-user>` | GitHub account hosting the repo + Pages | `octocat` |

---

## 1. What this template is

A **Swift 6, macOS-26-only menu bar app** (no Dock icon, no main window):

- SwiftUI `MenuBarExtra` app shell with a native dropdown menu and a `Settings` scene
- Local **SQLite persistence via GRDB**, with migrations, and UI that stays current through database observation (no manual refresh plumbing)
- Optional **global hotkey → floating HUD panel** module (non-activating `NSPanel` hosting SwiftUI)
- **Sparkle auto-updates** fed by an appcast on GitHub Pages
- **XcodeGen** project generation (no `.xcodeproj` in git), **Swift Testing** unit tests, **SwiftFormat**, GitHub Actions CI for build/test/lint on every push and a tag-triggered **sign → notarize → staple → GitHub Release** pipeline

Keep the shell, persistence pattern, and pipeline; swap the domain (models, services, views) for the new use case.

## 2. Assumptions

The consuming agent should treat these as the template's operating constraints and flag any that don't hold for the new project:

1. **macOS 26+ only**, Swift 6 language mode with strict concurrency, built with Xcode 26 (`macos-26` GitHub runners). Modern APIs (`@Observable`, Swift Testing, `glassEffect`) are used freely with no availability checks.
2. **Not sandboxed.** The template ships with `com.apple.security.app-sandbox: false` (the original app needed Apple Events automation and a private framework). If the new app doesn't need these, tighten the entitlements.
3. **Distribution outside the Mac App Store** via Developer ID signing + notarization + Sparkle. No TestFlight/MAS support.
4. **Single developer, GitHub-hosted.** Secrets live in GitHub Actions repo secrets; the appcast is served by GitHub Pages from `docs/`.
5. **LSUIElement app**: menu-bar-only, no Dock presence; quitting is a menu item.
6. An Apple Developer Program membership exists (needed for Developer ID certificate and notarization).

## 3. Repository layout

```
<repo>/
├── project.yml                  # XcodeGen manifest — the single source of truth for the project
├── ExportOptions.plist          # developer-id export config (method, teamID, manual signing)
├── .swiftformat                 # formatter config (also enforced in CI)
├── .gitignore                   # ignores *.xcodeproj (generated!), build/, DerivedData/, xcuserdata/
├── README.md
├── scripts/
│   └── build-release.sh         # local mirror of the CI release build (+ optional notarization)
├── .github/workflows/
│   ├── build.yml                # push/PR: generate → build+test → format lint
│   └── release.yml              # tag v*: sign → archive → export → notarize → staple → GitHub Release
├── docs/                        # GitHub Pages root
│   ├── index.html               # landing page
│   └── appcast.xml              # Sparkle update feed
├── <AppName>/                   # app sources (one flat module)
│   ├── App/                     #   @main entry, AppDelegate, AppState (composition root)
│   ├── Models/                  #   plain value types (structs/enums), GRDB record conformances
│   ├── Services/                #   long-lived @MainActor objects: monitors, controllers, updater
│   ├── Database/                #   DatabaseManager, Migrations, observation-backed stores
│   ├── Utilities/               #   Constants, Logger categories, small free functions
│   ├── Views/                   #   SwiftUI views, Theme, custom NSPanel subclasses
│   ├── Assets.xcassets          #   app icon, menu bar icon (template image), colorsets
│   ├── Info.plist               #   generated by XcodeGen from project.yml `info:` block
│   └── <AppName>.entitlements   #   generated by XcodeGen from project.yml `entitlements:` block
└── <AppName>Tests/              # Swift Testing unit tests (hosted in the app)
```

`*.xcodeproj` is **generated and gitignored**. Run `xcodegen generate` after cloning and after any file add/remove/rename or `project.yml` change.

## 4. Project generation (`project.yml`)

XcodeGen manifest skeleton — this is the shape the current repo uses, verbatim except for placeholders:

```yaml
name: <AppName>
options:
  bundleIdPrefix: <bundle-id-prefix>
  deploymentTarget:
    macOS: "26.0"

packages:
  GRDB:               { url: https://github.com/groue/GRDB.swift,                from: "7.0.0" }
  KeyboardShortcuts:  { url: https://github.com/sindresorhus/KeyboardShortcuts,  from: "2.0.0" }
  Sparkle:            { url: https://github.com/sparkle-project/Sparkle,         from: "2.1.0" }

settings:
  base:
    SWIFT_VERSION: "6.0"
    # Single source of truth for the version — Info.plist keys reference these.
    MARKETING_VERSION: "0.1.0"
    CURRENT_PROJECT_VERSION: "1"

targets:
  <AppName>:
    type: application
    platform: macOS
    sources: [{ path: <AppName> }]
    info:
      path: <AppName>/Info.plist
      properties:
        LSUIElement: true                                   # menu-bar-only, no Dock icon
        CFBundleDisplayName: <AppName>
        CFBundleName: <AppName>
        CFBundleShortVersionString: "$(MARKETING_VERSION)"  # never hardcode versions here
        CFBundleVersion: "$(CURRENT_PROJECT_VERSION)"
        SUFeedURL: "https://<github-user>.github.io/<AppName>/appcast.xml"
        SUPublicEDKey: "<sparkle-public-key>"               # from Sparkle's generate_keys
        # + NSAppleEventsUsageDescription etc. if the app automates other apps
    entitlements:
      path: <AppName>/<AppName>.entitlements
      properties:
        com.apple.security.app-sandbox: false               # tighten if possible
        com.apple.security.automation.apple-events: true    # only if scripting other apps
    settings:
      base:
        PRODUCT_BUNDLE_IDENTIFIER: <bundle-id>
        DEVELOPMENT_TEAM: <TEAMID>
        ASSETCATALOG_COMPILER_APPICON_NAME: AppIcon
        ENABLE_HARDENED_RUNTIME: YES                        # required for notarization
      configs:
        Debug:   { CODE_SIGN_IDENTITY: "Apple Development",         CODE_SIGN_STYLE: Automatic }
        Release: { CODE_SIGN_IDENTITY: "Developer ID Application",  CODE_SIGN_STYLE: Manual }
    dependencies:
      - package: GRDB
      - package: KeyboardShortcuts
      - package: Sparkle
      # + sdk: frameworks as needed (e.g. CoreAudio.framework, ServiceManagement.framework)

  <AppName>Tests:
    type: bundle.unit-test
    platform: macOS
    sources: [{ path: <AppName>Tests }]
    dependencies: [{ target: <AppName> }]     # hosted tests → @testable import works
    settings:
      base:
        PRODUCT_BUNDLE_IDENTIFIER: <bundle-id>.tests
        GENERATE_INFOPLIST_FILE: YES

schemes:
  <AppName>:
    build: { targets: { <AppName>: all } }
    run:   { config: Debug }
    test:  { config: Debug, targets: [<AppName>Tests] }   # makes `xcodebuild test` work
    archive: { config: Release }
```

Key decisions encoded here:

- **Version declared once** in `settings.base`; Info.plist references `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)`. A release bump touches exactly two lines.
- **Debug signs automatically, Release signs manually** with Developer ID. On machines without a certificate, build with `CODE_SIGNING_ALLOWED=NO`.
- **Explicit scheme with a test action** so CI can run `xcodebuild test -scheme <AppName>`.

## 5. Architecture conventions

### 5.1 App entry

```swift
@main
struct <AppName>App: App {
    @NSApplicationDelegateAdaptor(AppDelegate.self) private var appDelegate
    @State private var appState = AppState()
    @State private var updaterController = UpdaterController()

    var body: some Scene {
        MenuBarExtra {
            MenuBarView()
                .environment(appState)
                .onAppear { appDelegate.appState = appState }
        } label: {
            Image("MenuBarIcon").renderingMode(.template)   // template image → correct menu bar tinting
        }
        .menuBarExtraStyle(.menu)

        Settings {                                          // native Settings scene — no manual NSWindow
            SettingsView().environment(updaterController)
        }
    }
}
```

- A minimal `AppDelegate` exists **only** for `applicationWillTerminate`, which calls `appState.shutdown()` (removes notification observers, system listeners, hotkeys).
- Views open settings via `@Environment(\.openSettings)` + `NSApp.activate(ignoringOtherApps: true)` (needed because LSUIElement apps aren't active when the menu is clicked).
- **`.menu`-style MenuBarExtra constraint:** the menu renders only `Button`, `Text`, `Divider`, `Menu`, and `ForEach` of those. Any other view (stacks, images-as-layout, custom styles) is silently dropped. Design menu content accordingly.

### 5.2 Composition root

One `@MainActor @Observable final class AppState` constructs and owns every service, in dependency order, inside `init()`. If persistence fails to initialize, dependent services are set to `nil` and a `databaseAvailable` flag drives a warning row in the menu — the app degrades instead of crashing. `AppState` is injected with `.environment()`; views read it with `@Environment(AppState.self)`.

### 5.3 State & observation rules

- **`@Observable` everywhere** — no `ObservableObject`/`@Published`/Combine mirroring. App-level objects are created in `@State`, passed via `.environment()`.
- A service is `@Observable` **only if a view reads its state**; otherwise it's a plain `@MainActor final class`.
- Bridge KVO/publisher-based third-party state (e.g. Sparkle's `canCheckForUpdates`) into an `@Observable` property with a main-actor `Task` iterating `publisher.values` — not Combine `sink`/`assign` (Swift 6 sendability headaches).

### 5.4 Persistence (GRDB)

- `DatabaseManager: Sendable` wraps a `DatabaseQueue`. Two constructors:
  - `convenience init()` — on-disk DB in `~/Library/Application Support/<AppName>/`, WAL mode enabled
  - `static func inMemory()` — for tests
  - both funnel through a private `init(dbQueue:)` that runs a `DatabaseMigrator`
- Migrations are named (`"v1"`, `"v2"`, …) and registered in one `Migrations.swift`; never edit an existing migration, always append.
- Records are plain `Codable` structs with `FetchableRecord, PersistableRecord` conformance in an extension and snake_case `CodingKeys`.
- **UI never polls or reloads.** A `@MainActor @Observable` store (e.g. `TrackHistoryStore`) owns a `Task` that iterates `ValueObservation.tracking { … }.values(in: dbQueue)` and writes into an observable array. Menus, panels, and windows read the store; every DB write anywhere in the app propagates automatically.

### 5.5 Concurrency patterns

- Expensive or blocking work (image resize, synchronous DB insert, AppleScript round-trips) runs in `Task.detached` returning a `Sendable` value; the awaiting side stays on `@MainActor`.
- **Generation counters** guard in-flight work: bump a counter on state reset/new work; completions compare their captured generation and drop stale results.
- **Await in-flight tasks instead of sleep/retry**: if operation B must follow async operation A, store A's `Task` in a `private(set)` property and have B `await` it.
- Fire-and-forget callbacks from C APIs / notification centers hop to the main actor with `Task { @MainActor in … }` after extracting `Sendable` values on the calling thread.

### 5.6 Optional module: global hotkey + floating HUD panel

If the new app needs a Quick-Look-style HUD summoned by a hotkey:

- `KeyboardShortcuts.Name` extension defines the shortcut with a default; `KeyboardShortcuts.onKeyDown` (registered in `AppState.init`) triggers a controller; `KeyboardShortcuts.Recorder` in Settings lets the user rebind. Disable in `shutdown()`.
- The HUD is a `final class ...: NSPanel` with `[.borderless, .nonactivatingPanel, .utilityWindow]`, `level = .floating`, `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]`, content = `NSHostingView(rootView:)`, shown with `orderFrontRegardless()` + `makeKey()`.
- **Hard-won caveats encoded in the template — keep them:** a non-activating panel does not reliably receive `keyDown`/`flagsChanged` while another app is frontmost. The template polls `CGEventSource.keyState` (~30 Hz) for held navigation keys and `NSEvent.modifierFlags` for "dismiss on modifier release", with suppression logic so the summoning keystroke doesn't double-fire navigation. Reuse the panel class rather than rewriting it.

### 5.7 Logging

One extension declares `os.Logger` instances per category, subsystem = bundle id:

```swift
extension Logger {
    private static let subsystem = "<bundle-id>"
    static let app      = Logger(subsystem: subsystem, category: "app")
    static let database = Logger(subsystem: subsystem, category: "database")
    // one per service…
}
```

No `print`, no custom file loggers. Live tail: `log stream --predicate 'subsystem == "<bundle-id>"' --level debug`.

### 5.8 Theme & assets

- `enum <AppName>Theme` namespaces `Colors` / `Fonts` / `Spacing` / `Dimensions` as statics. Only add tokens that are actually used.
- Colors are **asset-catalog colorsets** with light/dark appearances, referenced through generated symbols (`Color(.textPrimary)`) — no hex parsing in code.
- Menu bar icon is a template image (`renderingMode(.template)`) so macOS handles tinting/selection.

## 6. Dependencies (and when to drop them)

| Package | Purpose | Drop if… |
|---|---|---|
| **GRDB 7** | SQLite persistence, migrations, `ValueObservation` | the app has no local data |
| **KeyboardShortcuts 2** | global hotkey + settings recorder UI | no global hotkey |
| **Sparkle 2** | auto-updates for non-MAS distribution | distributing via App Store |

Everything else is Apple frameworks. Add `sdk:` entries in `project.yml` for system frameworks (CoreAudio, ServiceManagement for launch-at-login via `SMAppService`, etc.).

## 7. Testing

- **Swift Testing** (`import Testing`, `@Test`, `#expect`, `#require`) — not XCTest.
- Tests are **hosted** in the app (target dependency in `project.yml`), so `@testable import <AppName>` reaches everything `internal`.
- Database tests use `DatabaseManager.inMemory()`; observation tests iterate `recent…Sequence()` and assert successive emissions.
- Suites testing `@MainActor` services are themselves annotated `@MainActor`.
- To test code that kicks off async work, expose the in-flight `Task` as `private(set)` and have the test `await task?.value` — no sleeps.
- Keep the domain parseable/testable: pure parsing (notification payloads → structs), source-detection enums, and sanitizers live in their own files, free of UI/system dependencies.

Run locally: `xcodebuild test -project <AppName>.xcodeproj -scheme <AppName> CODE_SIGNING_ALLOWED=NO`

## 8. CI (GitHub Actions)

### `build.yml` — every push to main + every PR

```
runs-on: macos-26
1. checkout
2. brew install xcodegen
3. xcodegen generate
4. xcodebuild -resolvePackageDependencies -project <AppName>.xcodeproj -scheme <AppName>
5. xcodebuild test -project <AppName>.xcodeproj -scheme <AppName> -configuration Debug CODE_SIGNING_ALLOWED=NO
--- separate job ---
6. brew install swiftformat && swiftformat --lint .
```

### `release.yml` — on tags `v*` (needs `permissions: contents: write`)

```
runs-on: macos-26
1. checkout; brew install xcodegen; xcodegen generate
2. import Developer ID cert:
   - create temp keychain (random password), import $APPLE_CERTIFICATE_P12 (base64 secret)
     with $APPLE_CERTIFICATE_PASSWORD, set-key-partition-list for codesign access,
     add to keychain search list; delete keychain in an `if: always()` cleanup step
3. xcodebuild archive -scheme <AppName> -configuration Release
     CODE_SIGN_IDENTITY="Developer ID Application" CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=<TEAMID>
4. xcodebuild -exportArchive -exportOptionsPlist ExportOptions.plist   # method: developer-id
5. ditto -c -k --keepParent <app> app.zip
6. xcrun notarytool submit app.zip --apple-id $APPLE_ID --password $APP_SPECIFIC_PASSWORD --team-id <TEAMID> --wait
7. xcrun stapler staple <app>; xcrun stapler validate <app>
8. ditto -c -k --keepParent <app> <AppName>-${TAG#v}.zip
9. softprops/action-gh-release@v2 → draft release with the zip, generated notes
```

**Required repo secrets:** `APPLE_CERTIFICATE_P12` (base64 of the Developer ID Application .p12), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`, `APP_SPECIFIC_PASSWORD` (from appleid.apple.com).

`ExportOptions.plist` contents: `method: developer-id`, `teamID: <TEAMID>`, `signingStyle: manual`, `signingCertificate: Developer ID Application`.

## 9. Release & auto-update pipeline (Sparkle)

**One-time setup for a new app:**
1. `generate_keys` (in Sparkle's release artifacts) → EdDSA keypair. Private key stays in the login keychain of the release machine; public key goes into `project.yml` as `SUPublicEDKey`.
2. Enable GitHub Pages, source = `docs/` on `main`. `SUFeedURL` = `https://<github-user>.github.io/<AppName>/appcast.xml`.
3. Seed `docs/appcast.xml` with an empty `<channel>`.

**Per-release checklist (in order):**
1. Bump `MARKETING_VERSION` (semver) and `CURRENT_PROJECT_VERSION` (monotonic integer) in `project.yml`; commit.
2. `git tag v<version> && git push --tags` → `release.yml` builds, notarizes, staples, and drafts the GitHub Release with `<AppName>-<version>.zip`.
3. Download the zip; sign it: `sign_update <AppName>-<version>.zip` → EdDSA signature + length.
4. Prepend an `<item>` to `docs/appcast.xml`:
   ```xml
   <item>
     <title>Version <version></title>
     <pubDate><RFC 822 date></pubDate>
     <sparkle:version><CURRENT_PROJECT_VERSION></sparkle:version>
     <sparkle:shortVersionString><version></sparkle:shortVersionString>
     <sparkle:minimumSystemVersion>26.0</sparkle:minimumSystemVersion>
     <description><![CDATA[ <h3>Changes</h3><ul><li>…</li></ul> ]]></description>
     <enclosure url="https://github.com/<github-user>/<AppName>/releases/download/v<version>/<AppName>-<version>.zip"
                sparkle:edSignature="<signature>" length="<bytes>" type="application/octet-stream" />
   </item>
   ```
5. Commit + push the appcast (Pages redeploys), then publish the draft release. Order matters: the enclosure URL 404s until the release is published, and Sparkle won't offer the update until the appcast is live — publish both promptly.

**Local release rehearsal:** `scripts/build-release.sh [--notarize]` mirrors CI (xcodegen → archive → export → codesign verify → optional `notarytool submit --wait` using a `store-credentials` keychain profile → zip). Note: pre-notarization `spctl -a` is *expected* to fail; the script tolerates it.

## 10. Local development workflow

**First run on a machine:**
```bash
brew install xcodegen swiftformat
git clone <repo> && cd <repo>
xcodegen generate
open <AppName>.xcodeproj        # Xcode: sign in / select team if running signed Debug builds
```

**Everyday loop:**
```bash
xcodegen generate                                     # after adding/removing files
xcodebuild -scheme <AppName> -configuration Debug build CODE_SIGNING_ALLOWED=NO
xcodebuild test -scheme <AppName> CODE_SIGNING_ALLOWED=NO
swiftformat .                                         # before committing
log stream --predicate 'subsystem == "<bundle-id>"' --level debug   # watch the app live
```

`CODE_SIGNING_ALLOWED=NO` is for machines without an Apple Development certificate; to actually *run* such a build, ad-hoc sign it: `codesign -s - -f --deep <path>/<AppName>.app`.

## 11. Bootstrap plan for a new project (for the consuming agent)

Execute in order; each step is independently verifiable.

1. **Init repo** with the layout from §3. Copy verbatim from the template: `.gitignore`, `.swiftformat`, `scripts/build-release.sh`, both workflow files, `ExportOptions.plist`. Copy `project.yml` and replace all placeholders (§4).
2. **Scaffold sources**: `App/` (App struct, AppDelegate, AppState skeleton), `Utilities/` (Constants, Logger extension), `Views/` (Theme, MenuBarView with a quit button, SettingsView with launch-at-login via `SMAppService` + update check), `Services/UpdaterController.swift`. If persisting data: `Database/` (DatabaseManager with on-disk/in-memory inits, Migrations with a `v1`, one observation-backed store) and `Models/` records. If hotkey/HUD: copy the panel + controller pair and the `KeyboardShortcuts.Name` extension.
3. **Assets**: AppIcon, template menu bar icon, colorsets for the theme tokens.
4. **Verify build+test locally**: `xcodegen generate` → `xcodebuild test … CODE_SIGNING_ALLOWED=NO`. Write the first tests (in-memory DB round-trip, any parser) before adding features.
5. **Run it**: build, ad-hoc sign if needed, `open` the app, confirm the menu bar item and `log stream` output.
6. **Wire GitHub**: push, confirm `build.yml` is green. Enable Pages (`docs/` on main).
7. **Signing/updates setup** (requires the human): export Developer ID Application cert as .p12; add the four secrets (§8); run Sparkle `generate_keys`; put the public key + feed URL in `project.yml`; seed `docs/appcast.xml`.
8. **Cut `v0.1.0`** following §9 and verify: notarized zip downloads cleanly (`spctl -a` passes on the stapled app), appcast validates, and a previous build offers the update.
